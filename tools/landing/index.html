什么是 Actor？把"互斥"变成执行模型的一部分

先用一个你大概率遇过的问题：余额 100，两个请求同时各扣 1 —— 都读到 100， 各自写回 99，扣了两次只少 1。这就是"读-改-写交错"。 常见的对策是加锁、串行队列、数据库事务，而 Actor 把这件事换了个做法： 状态私有 + 消息串行 + 失败有归属。

① 状态私有

状态只在 Actor 内部（本框架里就是 this.state）。外面拿不到引用，只能发消息 —— 所以不可能有人"在你读和写之间插一脚"。

② 消息串行

每个 Actor 一条 FIFO 邮箱，一次处理一条，处理完才取下一条 —— 读-改-写天然原子， 不需要锁。这是排队换来的，不是并行。

③ 失败有归属

handler 抛错 = 这个 Actor 崩溃，由父 Actor（监督者）按策略决定：重启出干净实例、 升级给祖父、或停下。而不是 try/catch 之后继续用脏状态。

监督树与失败语义

父 Actor 就是子 Actor 的监督者。one_for_one / rest_for_one / one_for_all 三种策略 + 重启强度（次数/时间窗）。

  • 孩子超出重启强度 → 升级给祖父决定，不会静默放弃
  • failure: 'crash' | 'retry' 显式选择：崩溃是信号，或按指数退避重试后进死信
  • 顶层耗尽强度 → system_failure 事件 + 如实停机

单 FIFO 邮箱与背压

每个 Actor 一条队列、串行处理：读-改-写不会交错，用不着锁（20 条并发消息，一条都不丢 —— 文档里有断言）。

  • 满邮箱语义显式：reject / drop-oldest / drop-newest
  • 拒绝/丢弃都留痕：mailbox_full 事件 + 计数器
  • 消息进死信队列：内存环 + 可选落盘（重启后还在）

持久化：快照或事件

mode: 'snapshot' 或 mode: 'events'，状态只放 this.state 就自动恢复；后端可插拔（内存 / 文件 / LevelDB / 自定义）。

  • 重启后状态还在（示例真跑：重启前 41 → 重启后 41）
  • 写入失败不静默：PersistenceError / 乐观锁冲突 PersistenceConflictError
  • 没配存储却要持久化 → 启动期就报错，不会等到第一个请求

零运行时依赖 · 无构建步骤

主仓库的 devDependencies 只有 typescript 与 @types/node；内核只用 Node 内置模块。

  • Node ≥ 24：靠原生类型剥离直接跑 .ts，没有编译产物
  • 唯一可选依赖是 LevelDB 后端（classic-level），缺失自动跳过
  • 数据库/缓存/邮件适配器不把驱动写进依赖：由调用方注入

分层装配与配置

内核只管 Actor；@actor/app 负责配置校验、依赖注入、模块与插件装配，@actor/web 只管路由与控制器。

  • 配置在启动期校验（unknown key / 类型错误 / 缺必填都当场报）
  • 依赖缺了就启动失败，而不是运行期拿到 undefined
  • 保留名有单一来源，撞了就报错，不靠约定

可观测性：一个出口

日志一处配好（logging），三类事件汇到一个出口；错误有显式出口（errors），后台失败不再不可见。

  • 请求级子日志自动带 requestId，meta 默认脱敏（token/cookie/password…）
  • 指标、全链路 Trace、OTLP 导出按需启用
  • 慢请求必记（不受采样影响）；诊断路由默认关闭、需 token

集群：Gossip + TCP 网关

对等节点用 Gossip 维护名册，用 TCP 网关（Protobuf 帧、可选双向 TLS）互相通信，跨节点 ask/tell 同一套 API。

  • 寻址是路径；本节点没有就查名册，再走网关
  • 心跳判活、失败计数、节点退出会被观察到
  • 共享存储才能跨节点交接有状态 Actor（文档明确写了边界）

数据层与中间件

@actor/data 给事件溯源、快照、仓储、Outbox、投影；@actor/db 用 defineModel 声明表并在三种方言上渲染。

  • 游标分页（并发写入下不漏不重），乐观锁冲突映射成 409
  • Redis / MongoDB / 邮件适配器都走受管资源：健康检查、保活、drain、关闭
  • 迁移有版本表、幂等、可回滚，中断可重入

工具链：CLI 与 testkit

actor 一条命令起项目、生成骨架、迁移、体检；@actor/testkit 提供虚拟时钟与故障注入。

  • generate 九种骨架，非破坏：不覆盖你的文件，只打印待粘贴的接线片段
  • 自定义命令：.actor/commands/*.ts 写好就是 actor 的子命令（子进程隔离执行）
  • 虚拟时钟把"等一小时"变成 0 真实毫秒

更便宜的等价问法：读-改-写之间夹着 await 吗？ 夹着就是危险区 —— 我们把它跑给你看过： 5 分钟改造演练（共享计数器 → Actor）。

做法并发正确性故障语义状态放哪主要代价
共享内存 + 手写锁 / 串行队列 能做对，但互斥由你负责：漏一处、异常路径没释放、换个入口忘了包就悄悄出错 靠 try/catch：兜住之后状态可能已写坏一半，还会继续服务 就在进程内存里 正确性依赖"记得加锁"；出问题最难查（现场早没了）
worker_threads + 手写 RPC 靠线程隔离，但要自己保证消息协议与顺序 要自己实现错误传播与重启 线程内/外部存储 序列化、协议、生命周期、重启全要自己写和维护
消息队列 + 无状态 worker 队列本身可靠，但状态在队列外面（数据库），跨消息的一致性回到事务问题 重试/死信要考虑幂等 外部存储（DB/Redis） 每次操作都要一次状态读写；本地开发与运维多一个中间件
框架 service 单例 + 数据库事务 事务覆盖单次请求；请求之间的读-改-写仍需自己串行 异常 → 500，状态靠事务回滚 数据库（进程内单例是无状态的） 内存态（房间、对局、连接）无处安放，只能外置
本框架：Actor 串行由模型保证：同 Actor 内读-改-写原子，不用锁（有可跑的对照实验） 显式：崩溃 → 监督树重启/升级；重启强度用尽 → 如实停机 + 事件 Actor 的 this.state（可配快照/事件持久化） 要接受"消息即边界"；Actor 里 await 慢 IO 会占住自己的邮箱

这个框架多给了什么

  • 失败语义是完整的：三种监督策略 + 重启强度 + 用尽后升级，直到顶层如实上报（不是"catch 住继续跑"）
  • 背压是显式的：邮箱满了三选一（reject / drop-oldest / drop-newest），且每次都留痕，不静默丢
  • 持久化两种模式：快照或事件，后端可插拔（内存／文件／LevelDB／自定义），写失败与乐观锁冲突都可见
  • 单进程与集群同一套 API：路径寻址 + gossip 名册 + TCP 网关，本地怎么发消息，跨节点就怎么发
  • 可观测性默认带：日志一个出口（事件分类 + 默认脱敏）、指标、全链路 Trace、慢请求必记、诊断路由
  • 零运行时依赖 + Node ≥ 24 无构建步骤：源码直接跑 TS，供应链短、调试不用对 sourcemap
  • 文档/示例即测试：指南里的示例块在 CI 真执行，语法糖必须与显式写法 deepStrictEqual 等价
  • 工具链把起步压到两条命令：new app + generate（非破坏、--dry-run 零写入）+ 迁移 + 体检

什么时候不要用它

这一节和上面一样重要 —— 用错地方是这套模型背锅，不是你的问题。

  • 纯 CRUD / 无状态 BFF：直接 Express/Fastify 更省事，Actor 只多一层概念。
  • 需要跨实体强一致事务：数据库事务更直接；Actor 只保证单个 Actor 内串行。
  • 读多写少的报表：走仓储/投影，别把查询塞进 Actor（串行世界会变瓶颈）。
  • handler 里大量 await 外部 IO：await 期间邮箱被占住，后续消息全排队 —— 把慢 IO 放到服务层，Actor 只做决策。
  • 单进程内存装不下的状态：Actor 是内存态 + 持久化，不是分布式 KV。
