# 全面审计（2026-10-07）

**审计结论一句话**：地基层面是干净的（无类型逃逸、无空捕获、无动态执行、SQL 全参数化、证书确实是测试专用、
600 条测试全绿、三道类型门禁可证伪），但审计**找出了 4 条高/严重问题**，其中 3 条我已独立复现：
① 客户端一次异常断开**能打崩进程**（WebSocket `error` 无人监听）；
② 遥测监听里抛异常**能挂死停机**、并让崩溃的 Actor **永不重启**；
③ 两份"`in-process` 条件写"能力声明**在同进程并发下不成立**（双写成功、事件重复落盘、返回值撒谎）；
④ `spawn()` 失败会**泄漏 cell**，且半初始化的 Actor **仍在处理消息**。
另外还有：被文档宣传的可运行示例**直接报错**、几处**我自己写的夸大措辞**、两处**时钟接缝不一致**、
若干**没有清理路径**的注册表。**这些都不在 `release:check` 的视野里**——这正是"绿了不等于能发布"。

## 一之二、安全维度发现 `[委派+我复核]`

### 🔴 高 ✅：网关默认**没有任何认证**，而 README 推荐非回环绑定

`gateway.ts:184`：

```js
this.requireHello = tlsUtil.isEnabled(this.tls) && this.tls.verifyNodeId !== false;
```

TLS 默认**关闭**（`config.ts:150` `ACTOR_TLS_ENABLED` 默认 false）→ `requireHello = false` → hello 握手门完全不生效 →
能连上端口的人可以直接发 `deliver`/`tell`/`stop` 帧，`remote.ts:330-344` 会把它们接到
`system.resolve(target).ask/tell/stop`（`stop` 帧 = 远程关掉任意 Actor）。

**我的复现（输出）**：

```
① requireHello = false | 未认证 deliver 是否被执行 → ["admin",{"pwn":1}]
```

而 `README.md:148` 明确推荐 `await a.listen({ host: '0.0.0.0', port: 9000 })`（`:407` 的 WS 示例也用 `0.0.0.0:8443`）
—— 库内**没有**任何"非回环必须 TLS/token"的守卫（`grep -rn "refusing to expose" packages/*/src/` 只命中 telnet 控制台，
**同类服务行为不一致**：控制台会拒绝，网关不会）。

### 🔴 高 ✅：gossip 可被投毒 + 注入任意拨号地址（SSRF）+ 条目无上限

TLS 关闭时 `tls-util.ts:248` 的 `_verifySender` **恒真**（`return { ok: true, skipped: true }`）→ `sender` 完全由报文决定；
`mergeState`（`gossip.ts:176-184`）只检查 `incoming.key === key` 就落表，**不校验 value 形状、不限制条目数、不检查 ts 上界**；
`_onGossipPayload` 还会把报文里的 `advertiseHost/port` 与最多 64 个 `peers[]` 地址学进拨号表。

**我的复现（输出）**：

```
① 注册表被写入 → {"host":"evil.example","port":9000}      （未来时间戳 + 大 nodeId 可永久压住 LWW）
② 被注入的拨号目标 → ["evil.example:1337","10.0.0.1:7200"] （本节点会主动去连这些地址）
```

（审计另测：1 秒灌 2 万条注册表条目，`packages/core/src/cluster/` 内不存在注册表/对等体数量上限。）

### 🔴 高 ✅：ws-server 分片消息**没有累计长度上限**，`maxPayloadBytes` 形同虚设

### 🟡 低 / 🔵 提示（我已复核的）

- ✅ **`applyEvent` 的 `__proto__`**（`actor.ts:99`）：`Object.assign(this.state, JSON.parse(...))` 会触发原型 setter。
  我的复现：`state.polluted = 42 | 是自有属性? false`（只影响该 state 实例，非全局污染，故为提示级）。
- **`verifyNodeId:false` 允许持任一合法证书冒充别的 nodeId**（与 `tls-util.ts:14-17` 的注释承诺冲突）。
- **控制帧不校验 ≤125 且不看 FIN**：1 MiB 的 PING 被原样回成 1 MiB 的 PONG（RFC 6455 §5.5）。
- **死信队列只有条数上限没有字节上限**，且每次 enqueue 全量读、超额全量重写（1 万条 × 8 MiB ≈ 80 GB，注释却称 "cannot fill the disk"）。
- **分帧/WS 读取按每个 data 事件 `Buffer.concat`**：8 MiB 帧按 64 KiB 到达要拷约 500 MiB（O(n²)）。
- **gossip `exportState()` 用 `.length` 当字节数**：中文等最多差 3 倍，可能让整帧超过 `maxFrameBytes` 被对端丢弃。
- **恒定时间比较有长度早退**；控制台认证失败无按 IP 退避。
- **`resolveActorModule` 不解析符号链接**（root 内指向外部的软链可绕过；`..foo/x.js` 会被误拒）。

### 🟠 中：两处定时逻辑绕过了可注入时钟（与我自己划定的范围不符）`[扫描]`

M5 的时钟接缝我明确写过范围："**纯逻辑定时**走时钟，网络 I/O 与停机安全边界保持真实时间"。
按这个标准，有两处**属于纯逻辑定时却没走时钟**：

2. `obs/alerting.ts:394` `setInterval(...)` 与 `:291` `evaluateOnce(now = Date.now())`
   —— 告警评估也是纯逻辑轮询，同样绕过时钟。

### 🔴 严重：客户端异常断开（RST）能打崩整个进程 `[委派+我复核]`

`packages/core/src/ops/ws-server.ts:85-92` 的 socket `error` 回调里 `this.emit('error', err)`，
而连接对象（`WebSocketConnection`）与 `packages/web/src/ws.ts:222-229` **都没有挂 `error` 监听**；
EventEmitter 在无 `error` 监听者时 `emit('error')` 会抛 `ERR_UNHANDLED_ERROR`，抛点就在 net socket 的
error 回调里 → uncaughtException → 进程退出。任何客户端 abortive close（移动端切网、代理、
k8s 杀连接）都能触发。

**我自己的复现（输出）**：

```
$ node -e "… server.on('connection', s => { s.on('close',()=>{}); s.on('message',()=>{}); }); … c.socket.resetAndDestroy(); …"
✗ 复核确认：进程被未捕获异常打崩 → ECONNRESET read ECONNRESET
```

### 🔴 高：遥测监听的异常能挂死停机、并中止崩溃监督 `[委派+我复核]`

所有 `system.emit(...)` 都没有保护（`logger` 与 `spanSink` 有 `try/catch`，见 `system.ts:634-641`、
`313-329`）。`_unregister` 在 `_finishStop()` 里、`envelope.resolve()` **之前**调用，于是：

**我自己的复现（输出）**：

```
① system.stop() → STOP_HUNG          （挂了 'actor_stopped' 监听器抛错）
② 崩溃后 restarts = 0                （挂了 'log' 监听器抛错 → 监督被中止）
```

后果有两层：① 一个抛错的 `system.on('actor_stopped'…)` 让 `cell.stop()` 永不 resolve →
`system.stop()` 的 `Promise.all` 永不 settle → **停机挂死**；② `_crash` 在 `crashing = true` 之后、
`_teardown()` 之前 `_log('actor_crash')` 抛错 → 该 Actor **永不重启**，且 `crashing` 永久为 true
（后续崩溃被 `if (this.crashing) return` 静默吞掉）。

### 🔴 高：`conditionalAppend: 'in-process'` 在同进程并发下**不成立**（数据完整性） `[委派+我复核]`

`packages/core/src/store/persistence.ts` 的 `appendEvent()` 是"先 `await _countFor()` 检查、
再 `await appendFile()` 写入"，中间**没有任何 per-key 串行化**（`FileStore`/`LevelStore` 都有
`_withLock`，持久化层没有），而 `capabilities()` 却报 `conditionalAppend: 'in-process'` ——
使用者正是靠这个字段判断"能不能多开一个 owner 写同一份存储"。

**我自己的复现（输出）**：

```
① 两个 owner 并发写 → fulfilled | fulfilled      （期望：其中一个被拒 PersistenceConflictError）
② 落盘事件数 = 2                                  （期望 1）
```

也就是说：两个节点/两个 system 共用存储时，同一个聚合会**写入重复事件**，而能力字段在说"进程内是安全的"。

## 五、建议的修复顺序（按"风险 ÷ 成本"排序）

**P0 —— 安全与数据完整性（建议立刻修，每条都有可复现脚本）**

1. **WebSocket 连接的 `error` 兜底**（F1 严重）：`WebSocketConnection` 构造时 `this.on('error', () => {})`，
   或让 `_frame` 写失败走 `close`。**一行改动，消除"一次 RST 打崩进程"**。
2. **遥测监听抛错不得影响内核**（F2 高）：给 `emit` 加 `_safeEmit()`（try/catch + 记日志），`_crash` 的
   `crashing` 清理放 `try/finally`。它同时修掉"停机挂死"与"崩溃后永不重启"。

   `FileRepository.update` 复用已有的 per-key 串行化（`_withLock`/`serialize`）；**同时**把 tmp 文件名
