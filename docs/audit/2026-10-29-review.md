## 2. P0：鉴权、进程可用性与数据完整性

### 2.1 【鉴权绕过】模块级插件被静默丢弃，`authPlugin` 装了也不鉴权

**位置**：[assembly.ts:426](packages/app/src/assembly.ts:426)（`middleware` getter）、[assembly.ts:431](packages/app/src/assembly.ts:431)（`routes` getter）、[assembly.ts:868-874](packages/app/src/assembly.ts:868)（`collect` 收集模块插件）

```ts
get middleware(): readonly unknown[] {
  const pluginMiddleware = (this.spec.plugins ?? []).flatMap((p) => p.middleware ?? []);
  return [...(this.spec.middleware ?? []), ...pluginMiddleware];
}
get routes(): readonly unknown[] {
  const pluginRoutes = (this.spec.plugins ?? []).flatMap((p) => p.routes ?? []);
  return [...this.routeSpecs, ...pluginRoutes];
}
```

`defineModule({ plugins })` 是公开 API（[assembly.ts:152](packages/app/src/assembly.ts:152)、`docs/design/m1-app-assembly.md:99`），`collect()` 也会把模块插件加入 `this.pluginSpecs`；但上面两个 getter 只读**顶层** `this.spec.plugins`。结果是：

- 插件的 `setup` / `onReady` 照常执行（密钥校验、服务注册都发生），**看起来装上了**；
- 插件贡献的 `middleware` 与 `routes` 一条都没进 HTTP 层；
- `authPlugin` 的鉴权中间件因此不存在，`auth: { required: true }` 只是控制器上的一个声明——**无 token 也能访问**；
- `uploadPlugin` / `debugPlugin` 装进模块时整片路由 404。

**触发（子代理实测）**：

```ts
modules: [defineModule({
  name: 'app',
  routes: [get('/me', defineController({ auth: { required: true }, handle: (_i, ctx) => ({ user: ctx.user ?? null }) }))],
  plugins: [authPlugin({ keys: [{ algorithm: 'HS256', key: SECRET }] })],
})],
plugins: [httpPlugin({ port: 0 })],
```

```
plugins seen by app = [ 'auth', 'http' ]   ← 确实“装上了”
middleware count = 0
GET /me 无 token → 200 {"user":null}       ← 应 401
```

**影响**：这是本轮最严重的一条。声明式鉴权被无声取消，日志/诊断没有任何异常；把安全插件放到业务模块（最自然的组织方式）就会中招。

**修复**：两个 getter 改读 `this.pluginSpecs`（拓扑序）；插件中间件按拓扑序而非声明序拼接；补一条“模块级 plugins 的 routes/middleware 必须生效”的回归测试（现有测试 **0 处**使用模块级 plugins）。

**证据**：✅ 实测（子代理），关键路径本次代码确认。

### 2.2 【远程 DoS】一条 WS 消息即可打崩进程

**位置**：[ws.ts:73](packages/web/src/ws.ts:73)（`matchRoute` 在 try 之外）、[ws.ts:252](packages/web/src/ws.ts:252)（`void handleMessage(...)`）、[routes.ts:214](packages/web/src/routes.ts:214)（`decodeURIComponent`）

```ts
socket.on('message', ((data, isBinary) => {
  void handleMessage(app, wsRoutes, app.middleware, socket, request, data, isBinary);
}) as never);
```

`matchRoute` 对路径段执行 `decodeURIComponent`，畸形百分号编码（如 `/%E0%A4%A`）直接抛 `URIError`；`void` 使 rejection 无人接管。Node 24 默认把未处理 rejection 当作致命错误。

**触发（子代理实测）**：连 `ws://host/chat/%E0%A4%A`，发任意一条消息 → 进程 exit 1。

**影响**：未认证远程 DoS。任何能连上 WS 端口的人都能让节点退出；若与 HTTP 同端口，则整个应用一起挂。

**修复**：`handleMessage` 整体 `try/catch`（含匹配、上下文构造、控制器），坏 URL 回 400；调用点改为 `.catch(err => log + close(1011))`，绝不再用 `void`。

**证据**：✅ 实测（子代理），代码路径本次确认。

### 2.3 【进程退出 ×2】HTTP 响应后日志抛错 / 端口占用

**位置**：[http.ts:262-270](packages/web/src/http.ts:262)（catch 里无条件 `writeHead(500)`）、[http.ts:252](packages/web/src/http.ts:252)（直接调 `app.logSink` 无保护）、[http.ts:277](packages/web/src/http.ts:277)（`server.listen` 无 `error` 监听）

**(a) 响应后日志抛错**：`res.end()` 之后才执行访问日志；用户在 `logging.logger` 里的实现抛错 → 进入 catch → `res.writeHead(500)` 在 headers 已发出时抛 `ERR_HTTP_HEADERS_SENT`，该错误又逃出 async IIFE → unhandled rejection → 进程退出。客户端看到的是 200，进程却死了。

**(b) 端口占用**：`await new Promise(resolve => server.listen(..., resolve))` 没有 `server.on('error')`。`EADDRINUSE` 变成 unhandled `'error'` event → 进程退出；同时 `start()` 永不 resolve/reject，调用方的兜底逻辑没有机会执行。

**触发（子代理实测）**：logger 在 `http:request` 抛错 → exit 1；先占端口再启动 → exit 1。

**修复**：catch 内先判 `res.headersSent || res.writableEnded`；所有用户回调（logger、事件）包 try/catch；`server.once('error', reject)`；整个请求 IIFE 加 `.catch()`。

**证据**：✅ 实测（子代理），代码确认。

### 2.4 【安全控制绕过】分片上传绕过扩展名 / MIME 白名单

**位置**：[upload/plugin.ts:181-191](packages/web/src/upload/plugin.ts:181)（`checkWhitelist`）、[:211](packages/web/src/upload/plugin.ts:211)（仅 multipart 调用）、[:381-385](packages/web/src/upload/plugin.ts:381)（分片 `complete` 直接 `put`）

```ts
const file = await options.storage.put(chunkStore.readAll(uploadId), {
  name: session.filename,
  mimeType: 'application/octet-stream',
  extension: extensionOf(session.filename),   // 客户端 init 时给的名字

```

`allowedExtensions` / `allowedMimeTypes` 是文档 15 明确推荐的安全配置；multipart 路径会校验，分片路径完全绕过。

**触发（子代理实测，`allowedExtensions:['png']`）**：

```
POST /uploads (multipart evil.php)   → 415
POST /uploads/chunked/init {filename:'evil.php'} → 201
PUT  /uploads/chunked/<id>/0          → 200
POST /uploads/chunked/<id>/complete   → 201 {"key":"…-.php"}
```

**影响**：上传目录出现 `.php/.html/.svg`。一旦被同域静态服务、反向代理或对象存储当可执行/可渲染内容托管，就是 RCE / 存储型 XSS。`storage.ts:51` 的“扩展名白名单”假设因此不成立。

**修复**：`init` 与 `complete` 都必须走白名单；扩展名只从白名单集合里选；补“分片路径同样 415”的测试。

**证据**：✅ 实测（子代理），代码确认。

### 2.5 【数据完整性】MongoDB `transaction()` 不是事务

**位置**：[mongodb.ts:87-94](packages/mongodb/src/adapters/mongodb.ts:87)、[client.ts:97-107](packages/mongodb/src/client.ts:97)

```ts
async transaction<T>(fn: (scoped: MongoNativeDb) => Promise<T>): Promise<T> {
  const session = client.startSession();
  try {
    return await session.withTransaction(() => fn(db));   // ← 传的是普通 db，不是 session
  } finally {
    await session.endSession().catch(() => undefined);
  }
}
```

`withTransaction` 只负责开启/提交/中止会话；官方驱动的每个操作必须收到 `options.session` 才会加入事务。这里既没把 session 传给回调，`DocumentClient` 的薄封装又把 `options` 参数整个丢掉了（`updateOne: (f, u) => native.updateOne(f, u)`），调用方**连手动传 `{session}` 的途径都没有**。

**触发（子代理假驱动实测）**：

```ts
await db.transaction(async (tx) => {
  await tx.collection('accounts').updateOne({ _id: 'a' }, { $inc: { balance: -100 } });
  await tx.collection('accounts').updateOne({ _id: 'b' }, { $inc: { balance: 100 } });
  throw new Error('业务失败');   // 期望整体回滚
});
```

```
insertOne 收到的 options = undefined
→ 是否带 session: false
```

**影响**：转账只扣不加；并发读者能看到中间态；`withTransaction` 的自动重试会让非幂等写在事务外**重复执行**。文档 `docs/guide/internals/10-mongodb.md:33-34` 与 `docs/design/m7-multi-database.md:481` 都把它宣传为“与 SQL 侧同签名”的真事务。

**修复**：`startSession()` 后把 session 透传到每个操作（`DocumentClient` 持有 session，`collection()` 默认注入）；补回 `insertOne/updateOne/…` 的 `options`；测试断言“操作确实带了 session”，而不是“开了一个 session”。

**证据**：✅ 实测（子代理），代码确认。

### 2.6 【数据损坏 + 永久不可启动】聚合 + 快照缓存恢复后 seq 归零

**位置**：[aggregate.ts:295](packages/data/src/aggregate.ts:295)（`let seq = this[SEQ_KEY] ?? 0`）、[aggregate.ts:317](packages/data/src/aggregate.ts:317)（`incoming.seq ?? 计数 + 1`）、[events.ts:379-403](packages/data/src/events.ts:379)（`readLog` 只返回 payload）、[actor-cell.ts:1157](packages/core/src/actor/actor-cell.ts:1157)（`upcast` 后再 `applyEvent`）

**根因链**：

1. 聚合的 `applyEvent` 期望收到**事件信封**（带 `seq`）；但内核 `persistEvents` / `_restore` 在调用前先走 `evolution.upcast`，而 `upcast` 返回的是 **payload**；
2. 因此 `resolveIncoming` 判定“不是信封”，`seq = null`，聚合只能按“应用了几条”递增；
3. 无快照时，全量重放恰好把计数器推到“最后一条”，碰巧正确；
4. 启用 `persistence:{mode:'events', snapshot:{every:N}}`（m3 文档推荐的组合）后，从快照恢复时**只重放增量**（常常为空），计数器从 0 开始；下一条命令写入 `seq=1`；
5. 下次启动 `readLog` 的连续性检查发现 `1` 不大于前一条 `2` → `EventSchemaError`，**该 Actor 永久无法启动**；删快照也没用，因为校验的是整段日志。

**触发（子代理实测）**：

```
阶段2 日志 seq: [1,2,1]（期望 [1,2,3]）
阶段3 启动失败: EventSchemaError - 事件日志第 3 条的 seq=1 没有大于前一条的 seq=2
```

**影响**：设计文档重点推荐的“快照是缓存、日志是真相”组合，在第二次重启后就把 Actor 锁死。现有测试只覆盖“快照被丢弃后从 0 重放”，所以全绿。

**修复**：seq 不能建立在“应用条数”上。三选一（建议前两者之一）：内核把 `seq` 一并交给 `applyEvent`；写入期保留信封、只在聚合内部解包；把 `atSeq` 通过 `postRecover` 显式交给聚合。补“快照恢复后继续写入 → 重启 → 再写入”的回归。

**证据**：✅ 实测（子代理），代码链本次确认。

### 2.7 【静默丢写】SQLite 事务不串行、不隔离

**位置**：[sqlite.ts:72-87](packages/db/src/drivers/sqlite.ts:72)

```ts
async transaction<R>(fn: (scoped: Runner) => Promise<R>): Promise<R> {
  db.exec('BEGIN');
  try {
    const result = await fn(api);   // ← 同一个 db，所有并发调用都看得到
    db.exec('COMMIT');
    return result;
  } catch (err) { db.exec('ROLLBACK'); throw err; }
}
```

`node:sqlite` 是单连接、同步 API；`await fn(api)` 的每个 await 点都会让出事件循环，**任何其他请求的写操作都会落进这个事务**。事务回滚时，无关写入一起消失，而调用方早已收到 `affected=1`。

**触发（子代理实测）**：

```
无关 INSERT affected=1 → 事务回滚 → 最终表内容 []
并发事务 → cannot start a transaction within a transaction
```

**影响**：SQLite 是 `databasePlugin` 的默认方言；默认配置下就可能出现“写成功但数据没了”。并发事务还会直接抛错。

**修复**：事务必须串行化（队列/互斥）并让事务内的 runner 与外部 runner 隔离；或改用“每次事务独立连接”（sqlite 单文件多连接 + WAL）。现有 `Runner.transaction` 契约应明确“是否串行、如何隔离”。

**证据**：✅ 实测（子代理），代码确认。

### 2.8 【静默丢写】SQL 仓储的 `activeRunner` 把外部写卷进事务

**位置**：[sql.ts:128-140](packages/data/src/repository/sql.ts:128)（`serialize` 只包 transaction）、[:296-310](packages/data/src/repository/sql.ts:296)（`activeRunner = scoped`）

```ts
transaction<R>(fn) {
  return serialize(async () => {
    if (!runner.transaction) return fn(api);
    return runner.transaction(async (scoped) => {
      const previous = activeRunner;
      activeRunner = scoped;          // ← 实例级可变字段
      try { return await fn(api); } finally { activeRunner = previous; }
    });
  });
}
```

只有 `transaction` 进了 `serialize` 队列；`update/insert/delete/find` 直接读 `activeRunner`。事务进行期间，**事务外的并发调用也会使用事务连接**，并在回滚时一起丢失。

**触发（子代理假 pg runner 实测）**：事务中 `await sleep`，另一路 `update()` 返回成功；事务回滚后该行未变。

**影响**：与 2.7 同类的静默丢写，但发生在数据层默认仓储上；业务侧无法从返回值察觉。

**修复**：事务连接不能放在实例字段上。把 runner 作为参数显式传给仓储操作（每步 `useRunner`），或使用 AsyncLocalStorage 隔离上下文；`serialize` 应覆盖所有写操作。

**证据**：✅ 实测（子代理），代码确认。

## 6. 测试与质量门禁评估

### 6.1 做得好的地方

1. **测试数量与组织**：1,116 个用例、按包分目录、`node:test` 零依赖；关键安全面（mTLS、CRL、nodeId 绑定、WS 分片/控制帧、TLS 降级）都有真实 socket 级测试。
2. **门禁意识**：`test/unit-kernel-surface.test.js` 检查公开面漂移；`test/unit-package-matrices.test.js` 检查测试/类型/文档接线；`release-check` 检查 tarball 内容与发布路径；`unit-docs-site` 检查文档与示例逐字一致。这些门禁本身还有“能证伪”的用例，做法值得肯定。
3. **失败可见性**：大量“降级必须可见”的事件（`fencing_skipped`、`registry_rejected`、`mailbox_full`、`dead_letter`），而不是静默吞掉。
4. **安全默认值**：Gateway / WS / Telnet 的非回环明文拒绝、TLS 双开关组合拒绝、CRL/denylist、SMTP……方向正确。
5. **文档与类型**：`docs/design` 对语义边界（fencing 窗口、at-least-once、快照是缓存）写得比多数开源项目清楚。

### 6.2 测试的结构性缺口（比“少几条用例”更重要）

| 缺口 | 具体表现 | 建议 |
|---|---|---|
| **断言“调用”而非“效果”** | Mongo 事务只看 `sessions === 1`，不看操作是否带 session；邮件只看 `.eml` 存在，不看 CTE；订阅总是先 `off()` 再 `close()` | 断言最终状态/副作用（盘上内容、驱动收到的 options、解码后的正文） |

- **安全默认值与“降级可见”**：Gateway/WS/Telnet 的非回环明文拒绝、TLS 双开关组合拒绝、`fencing_skipped`/`registry_rejected` 等事件，属于很多框架做不到的细节。
- **文档纪律**：设计文档把“挡不住的窗口”“at-least-once”“快照是缓存”写清楚；文档站断链/示例执行/事实门禁都接进了 CI。
- **零运行时依赖 + 手写 Protobuf/WS/TLS 工具**：实现质量总体不错，`frame decoder`、CRC、原子写、随机 tmp 名、进程级写锁都考虑了真实故障模式。
- **测试基础设施**：可注入时钟、testkit 虚拟时钟、假驱动、契约套件、发布路径 dry-run，说明作者理解“可验证性”比“多写代码”更重要。
- **前一轮审计的修复质量**：TLS 守卫、WS 分片上限、gossip 条目上限、FilePersistence 锁、`_abandon`（根 Actor）等都有可证伪的回归测试；本报告刻意不重复这些已修项。

## 9. 未能验证 / 边界

- **真实后端**：无 Redis / Mongo（副本集）/ PostgreSQL / MySQL / SQL Server / SMTP 服务，相关结论来自假驱动、SQL 文本与行形状推断；H5（漂移假阳性）与 D11（唯一约束错误码）需真实服务确认。
- **Windows**：`URL.pathname` 在 Windows 上返回 `/C:/...` 是按 Node 语义推断；本地只用“含空格路径”复现了 `%20`。
- **浏览器/反代**：CSRF、跨站 WebSocket、共享端口在真实反代后的暴露面未实测。
- **长跑/soak**：连接/内存/句柄曲线未做小时级观测；R1/R5 的泄漏量按代码路径推算。
- **`npm audit`**：环境离线，未做依赖漏洞扫描。
- **`@actor/db` 的声明编译**：`tsconfig.types.json` 未映射该包，本次只做了源码级比对，未把“声明面编译”跑起来。
