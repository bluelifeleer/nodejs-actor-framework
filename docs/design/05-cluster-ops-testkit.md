# 集群治理、运维与 TestKit（设计草案）

> 对应开放问题 Q8。现在集群只有"**发现**"（按名字找到 Actor 并懒连接），缺"**治理**"（谁拥有、怎么交接、下线怎么办）。

## 1. 集群：从发现到所有权

### 1.1 现状与缺口

| 能力 | 现状 | 缺口 |
|---|---|---|
| 成员发现 | ✅ gossip（LWW + 墓碑 + 心跳 + 剔除） | — |
| 按名字寻址 | ✅ `ctx.ask('room-2', …)` | — |
| 跨节点回信 | ✅ 帧带 sender 地址 | — |
| **分片所有权** | ❌ 示例里是 `房间号 % 节点数` 手写 | 需要框架级所有权 + 成员变更时重算 |
| **优雅交接** | ❌ 节点下线 = 它上面的 Actor 全丢 | 需要 drain + 状态转移 + 所有权切换 |
| **Singleton** | ❌ | 需要"全集群唯一"的 Actor（定时任务/撮合/发号） |
| **脑裂处理** | ❌（gossip 是 AP） | 需要明确"单主保证"的边界与降级策略 |

### 1.2 分片模型

```
shard = 一批 Actor 的所有权单元（例如 shard-0..shard-255）
ring  = 一致性哈希环（虚拟节点，减少成员变更时的迁移量）
owner(shard) = ring 上顺时针第一个存活成员
```

- Actor 归属 shard：`shard = hash(actorPath) % shardCount`（对**路径**哈希，保证同一实体稳定）。
- 成员变更 → 只有落在变更点区间的 shard 需要迁移（虚拟节点让迁移量≈1/N）。
- **shard 数是运维常量**（改它等于全量重分布），文档必须写死这条。

### 1.3 交接协议（最关键、最容易做错）

```
扩容/缩容/故障 三种触发路径不同：
  扩容：新成员加入 → 老 owner 主动让出区间内的 shard（优雅交接）
  缩容：成员收到 drain 指令 → 主动交接全部 shard → 再退出
  故障：成员失联 → 心跳超时 → 其他成员重算所有权（无交接，靠状态恢复）

优雅交接步骤（转移期间不允许双主）：
  1. 冻结：老 owner 停止把这些 shard 的新消息交给 Actor（网关/路由层返回"重定向到新 owner"）
  2. 排空：等在途消息处理完（有上限，超时则记录并继续）
  3. 导出：把 Actor 状态导出为「快照 + 事件 offset」（走已有的 saveSnapshot / events）
  4. 转移：通过集群消息把状态发给新 owner（大数据分块；失败可重试）
  5. 装载：新 owner 恢复状态，从 offset 继续
  6. 切换：所有权 epoch +1（**fencing token**：所有发往该 shard 的消息带 epoch，旧 epoch 一律拒绝）
  7. 释放：老 owner 丢弃本地 Actor
```

**要点**：
- **fencing token 是防双主的唯一可靠手段**（时间戳/租约在时钟漂移下不可靠）。
- 交接必须**幂等可重试**（第 4 步失败就重来，不应产生两个 owner）。
- 不可交接的 Actor 必须显式声明：持有 socket/文件句柄/定时器的 Actor（如会话 Actor）标 `transferable: false` → 节点下线时连接断开，客户端重连（这是正确语义，不要假装能迁 socket）。
- **故障路径没有交接**：靠"状态可恢复"（快照/事件）+ 幂等业务；文档要区分"优雅下线"与"崩溃"两种质量等级。

### 1.4 Singleton

- 就是"shardCount = 1"的特例：全集群唯一 owner，成员变更时交接（接管有延迟，需容忍短暂无主或短暂双主由 fencing 拦住）。
- 用途：定时任务、发号器、撮合、集群级指标聚合。
- 用法草案：`system.spawnSingleton(LeaderElection, { id: 'cron-leader' })`。
- **明确边界**：singleton 是"尽力而为的单例"（基于 gossip 所有权），不是分布式锁；需要强一致的场景请接 etcd/consul（文档给适配接口）。

### 1.5 脑裂与一致性边界（必须写清，不能含糊）

| 场景 | 行为 |
|---|---|
| 网络分区，少数派 | 少数派**拒绝写**（返回 503 + 重试提示），避免双主 |
| 网络分区，多数派 | 继续服务；少数派节点上的 Actor 变为"不可达"，客户端重试到多数派 |
| gossip 未收敛期间 | 所有权切换有窗口；用 fencing token 防止旧 owner 生效 |
| 集群整体重启 | 靠持久化状态恢复；不需要选主（每个 shard 的 owner 由确定性哈希决定） |

> 结论：**分片所有权做到"多数派可写 + fencing 防双主"就够用**；不要试图在 gossip 上做线性一致，那会变成另一个 Raft。

## 2. 运维

### 2.1 健康检查

| 端点 | 语义 | 判定 |
|---|---|---|
| `/health/live` | 进程活着（不检查依赖） | 永远 200（除非事件循环被阻塞） |
| `/health/ready` | 可以接流量 | 插件 setup 完成 + 存储可写 + gossip 已收敛（可配容忍度）+ 必需迁移已应用 |
| `/health/startup` | 首次启动完成 | 用于 K8s startupProbe |

**要点**：readiness 必须能表达"我还能服务但别给我新流量"（draining 状态 → 503 + `Connection: close`）。

### 2.2 优雅下线（drain）顺序

```
收到 SIGTERM
 1. readiness → false（LB 摘流量），等待摘除传播（可配，默认 5s）
 2. 停止接受新连接；HTTP 返回 503 + Retry-After
 3. 等待在途请求完成（预算内）
 4. 交接分片（§1.3）——若集群开启
 5. 停止 Actor：停止接新消息 → 排空邮箱（有界）→ 写快照 → postStop
 6. 关闭插件（逆序）→ 关闭传输 → 刷新日志/指标
 7. 退出（超时则强杀，但要记录哪些 Actor 没停干净 —— 现在内核已有 system_stop_timeout）
```
**预算**：整体有 deadline（默认 30s），每步有子预算；超预算时记录并继续下一步，**绝不无限等**。

### 2.3 配置热加载与 drain 的交互

- 热加载期间收到 SIGTERM → 中止加载，直接进入 drain（半套新配置比旧配置更危险）。
- 交接期间禁止热加载（配置来源可能正在变）。

## 3. 可观测性

| 维度 | 现状 | 目标 |
|---|---|---|
| 指标 | ✅ Prometheus 文本 + 框架形状指标 | 真实 OTel 导出（metric + trace），保留 Prometheus |
| Trace | ✅ 跨节点传播已修（帧带 trace） | 导出到 OTLP；与 HTTP span 串起来（request span → actor span） |
| 日志 | ✅ 结构化事件 + 采样 | 适配 pino/winston；统一字段 `requestId/traceId/actorPath/nodeId`；敏感值脱敏 |
| 告警 | ✅ `src/obs/alerting.js` + Prometheus 规则 | 加集群维度（shard 迁移失败、所有权震荡、gossip 不收敛、单例真空期） |
| 审计 | ❌ | 鉴权拒绝、敏感操作、状态迁移（谁在什么时候做了什么）——高合规要求场景必需 |
| 诊断 | 部分（`inspect()`、控制台） | Actor 清单/邮箱深度/监督树导出为可视化数据；`/debug/actors`（仅内网 + 鉴权） |

**指标基数**：内核已有 `maxPerActorSeries` 上限；分片维度（shard 标签）基数需受控，文档给推荐标签集。

## 4. TestKit

现在测试全靠手写 helpers（`test/helpers.js`），用户写业务测试会更痛。目标能力：

| 能力 | 解决什么 | 依赖 |
|---|---|---|
| **虚拟时钟** | 定时器/超时/退避测试不用 sleep，且确定性 | 内核可注入 clock（doc 01 §3.1） |
| **TestSystem 工厂** | 一行起系统、自动清理、隔离的临时存储 | 现有 + 容器覆盖 |
| **探针 Actor** | `probe.expectMsg({type:'x'})` / `expectNoMsg(100)` | 内核 ask/邮箱 |
| **HTTP 测试客户端** | 不绑端口直接调路由，断言状态码/响应体/中间件副作用 | Web 层路由可注入调用 |
| **持久化 fixture** | 预置快照/事件、断言落盘结果、模拟半写崩溃 | 现有 store |
| **故障注入** | 让指定 Actor 崩溃/变慢/丢消息/时钟跳变/存储报错 | 内核中间件 + clock |
| **确定性并发** | 固定调度顺序复现竞态（种子化） | 调度器可注入 |
| **契约测试** | 路由表 vs OpenAPI、消息 schema vs 事件定义 | 路由表导出 + schema |

**设计原则**：TestKit 必须能测"用户自己的 Actor"，而不只是框架自身；API 要能一眼看出断言失败的原因（期望收到什么、实际收到什么、邮箱里还剩什么）。
