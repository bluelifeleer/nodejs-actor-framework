# 路线图、版本策略与明确不做（设计草案）

> 本文汇总里程碑、验收标准、兼容承诺，以及**我们拒绝做的事**（防止项目漂移成"第二个 NestJS"）。

## 1. 里程碑

前置：**Q1（语言）/Q2（包结构）/Q3（控制器语义）必须先定**，否则 M0 的返工成本最高。

| 里程碑 | 目标 | 交付物 | 验收标准 |
|---|---|---|---|
| **M0 内核瘦身与硬化** | 内核真正可独立使用 + 业务必需原语 | ① `index.js` 公共面瘦身（不 eager 加载插件，S2）② 定时器 + 可注入时钟 ③ 消息中间件 ④ 消息 schema 校验（失败进死信）⑤ 可换调度器/邮箱/监督策略注册表 ⑥ readiness/liveness + drain 雏形 | 无 node_modules 且**只装 core** 时单测全绿；1 万 Actor 规模测试无性能回归；定时器在崩溃重启后不残留 |
| **M1 配置·DI·插件 SDK** | 让"用户配置/扩展/插件"变成正式能力（doc 02） | 配置分层 + schema + 校验错误（含来源）+ 热加载；容器（singleton/scoped/factory + 生命周期）；`definePlugin`（requires/provides/config/路由/健康检查/CLI）+ 依赖图 + 回滚；插件模板 | 写一个第三方插件不改内核代码即可提供：配置节 + 服务 + 路由 + 健康检查；插件依赖成环时启动失败并打印环 |
| **M2 Web 层** | 路由/控制器/校验/鉴权（doc 03） | `Router` + 控制器基类/纯函数 + `ctx.actor()` 桥 + 请求作用域 + 内置校验 + zod/ajv 适配 + 路由级授权 + **消息级 guard** + 错误映射 + WS/SSE 复用会话 Actor | 一份示例应用（用户 CRUD + 房间加入）在同进程与"接入层+节点分离"两种部署下**控制器代码零改动**；错误映射有逐条用例 |
| **M3 数据层与演进** | 仓储 + 事件溯源 + 演进（doc 04） | `Repository` + 文件/内存/SQL 薄适配 + `Aggregate`（expectedVersion）+ upcast 注册表 + 快照版本策略 + 迁移框架 + outbox + 投影（断点/重建/去重） | 改一次状态结构的真实演习：v1 数据在 v3 代码下可读（有 upcast 单测）；投影可从 0 重建且不丢不重（带去重用例）；outbox 至少一次 + 消费幂等有测试 |
| **M4 集群治理** | 分片所有权 + singleton + 交接（doc 05 §1） | hash ring + 所有权 + fencing token + 优雅交接 + singleton + 少数派拒写 + 迁移指标 | 3 节点集群：下线一个节点，其 shard 全部交接且**无消息丢失**（有测试）；旧 owner 用旧 epoch 发消息必须被拒（fencing 测试）；扩缩容迁移量符合预期 |
| **M5 产品化** | 能用、好学、可维护 | TestKit（虚拟时钟/探针/HTTP 测试/故障注入）+ CLI（脚手架、迁移、诊断）+ OTel 真实导出 + 日志适配 + 文档站与 API 参考 + 迁移指南 + CHANGELOG/版本策略 | 新人按文档在 30 分钟内跑通"CRUD + Actor + 持久化 + 测试"；`actor new app` 可生成可运行骨架 |

**建议顺序**：M0 → M1 → M2（先能写 Web 业务）→ M3 → M4 → M5。理由：M0/M1 是所有上层的地基；M2 决定"像不像一个 Web 框架"；M3/M4 是生产深度；M5 是长期成本。

## 2. 版本与兼容策略

### 2.1 语义化版本

| 变化 | 版本 | 例子 |
|---|---|---|
| 新增可选能力、新增插件、修 bug | minor / patch | 加定时器、加中间件 |
| 改默认值、改错误类型、改方法签名 | **major** | `ctx.ask` 参数从位置改为对象 |
| 内核语义变化（如监督默认策略） | **major** | 默认从 `one_for_one` 改为 `rest_for_one` |
| 用户消息契约（用户代码） | 不受框架版本约束 | 用户自己管 |

### 2.2 弃用流程

1. minor 版本：标记 `@deprecated`（类型 + 运行期首次使用时警告一次），文档写替代方案。
2. 下一个 minor：保留但警告升级为"将在下个 major 移除"。
3. 下一个 major：移除，并写入迁移指南（附 codemod 脚本，能自动就自动）。

**内核"实验性"标记**：新能力头两个 minor 标 `experimental`，明确"可能 breaking"，避免用户过早依赖。

### 2.3 支持矩阵与发布检查清单

- Node：只支持**当前 LTS**（文档标明具体版本），CJS 为主（若 Q1 选 TS，产出 CJS + ESM 双产物 + `exports` 映射 + `.d.ts`）。
- 发布前必须：全量测试（含有依赖/无依赖两条路径）✓、typecheck、规模测试无回归、`npm pack` 内容检查（不含测试证书）、CHANGELOG、示例全部可跑。
- 目前这些**已经具备**（README 里的测试矩阵与打包检查），M5 只是把它们固化成脚本 + CI。

## 3. 明确不做（Non-goals）

| 不做 | 理由 | 替代 |
|---|---|---|
| **自研 ORM / 查询构建器** | 无底洞，且与 Actor 优势无关 | `Repository` 适配器 + 提供 Prisma/Drizzle/Kysely 示例 |
| **模板引擎 / 视图层** | 前后端分离已是主流 | 返回 JSON；需要 SSR 就接现成引擎（给示例） |
| **装饰器作为默认 API** | 需要构建步骤 + 元数据，破坏"零构建、纯 CJS 可用" | 显式 builder 为默认；TS 用户可选装饰器包（M5，取决于 Q1） |
| **管理后台 UI** | 与框架定位无关，维护成本高 | 提供 `/debug/actors` 数据接口，UI 由用户或工具做 |
| **分布式事务 / 两阶段提交** | 复杂度极高，收益低 | saga/process manager + outbox + 幂等消费 |
| **自研强一致共识（Raft）** | gossip 是 AP；强一致需求应交专业组件 | 分片所有权用"多数派 + fencing"；强一致场景给 etcd/consul 适配接口 |
| **自动弹性伸缩 / 自动 rebalance** | 需要稳定的成员视图与运维策略，早期做得越多越危险 | 手动扩缩容 + 优雅交接；指标先观测一版再考虑 |
| **前端框架能力（SSR 路由、hydration）** | 完全不同的领域 | 不做；给集成示例 |

## 4. 开放问题汇总（决策清单）

| # | 问题 | 影响面 | 我的建议 |
|---|---|---|---|
| **Q1** | 源码语言：JS+CJS+`.d.ts`（现状）还是 TS 源码+构建 | **最大分叉**：决定装饰器/DI 体验、构建链、发布产物 | 倾向 TS 源码 + 双产物，但**先确认是否接受引入构建步骤**；若不接受，则装饰器方案作废，路由/DI 全部走显式 API |
| **Q2** | 包结构：monorepo 多包（A）还是单包多入口（B） | 决定"Actor 独立可用"的强度 | A（唯一能机械保证的方案） |
| **Q3** | 控制器：无状态（推荐）还是 Actor 支撑 | HTTP 并发模型与文档叙事 | 无状态为默认，按路由 opt-in |
| **Q4** | 路由：显式 builder / 文件路由 / 装饰器 | 与 Q1 强相关 | 显式 builder 为默认 |
| **Q5** | 数据主线：事件溯源优先还是仓储优先 | M3 实现顺序与示例重心 | 事件溯源为差异化主线，CRUD 作为轻量路径 |
| **Q6** | 校验：内置极简 + 适配器，还是直接依赖 zod | web 包是否零依赖 | 内置 + 适配器（core 零依赖是底线） |
| **Q7** | 目标用户：团队内部还是公开发布 npm | 文档/版本/兼容承诺强度 | 若公开：M5 的文档站与版本策略是必做，不能省 |
| **Q8** | 集群范围：只做发现（现状）还是加分片与交接 | M4 是否进主线 | 加分片与优雅交接，但不做自动 rebalance |

各章节还有局部决策（A1–A5、B1–B5、C1–C5、D1–D6、E1–E6），分别见对应文档末节。

## 5. 建议的下一步

1. **你先拍 Q1/Q2/Q3**（语言、包结构、控制器语义）——这三个决定后面所有 API 形态，越早定越省返工。
2. 我按 M0 出一版**详细设计 + 接口草案**（定时器/中间件/校验/瘦身公共面的确切签名与测试计划），仍然不写实现，供你 review。
3. 你确认 M0 设计后，再开始实现；每个里程碑结束时按上面的验收标准出证据。

> 当前仓库状态提醒：内核 + 运维插件 + 接入层参考实现已完成（279 个用例全绿），但这套设计文档描述的是**内核之上的框架产品**，其中 M0 的第 ① 项（公共面瘦身）会**改动现有 `index.js` 的导出方式**，属于对现有代码的 breaking 变更，需要单独确认。
